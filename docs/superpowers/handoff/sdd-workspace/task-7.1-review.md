### Issues
#### Critical
(none)
#### Important
1. state.rs `from_preset_with` (the `if let Some(prog) = compile_section(... "per_frame_init" ...)` block) and custom.rs `WaveState::load`/`ShapeState::load` (the init branches) always load this preset's values, plus q_init for waves and shapes, before the init code runs. The C++ does this only for an instant load:
   - **Instant load** (blend 0: first preset, hard cuts, most hotkeys; plugin.cpp:7251-7259). The states are swapped before `Import`, so `this == m_pState`, and the init code sees its own values plus live inputs. Rust matches, except that the C++ q and monitor are the stale `q_values_after_init_code` left in that CState slot by a preset it held earlier; Rust's 0 is fine.
   - **Blended load** (auto rotation `m_fBlendTimeAuto` 2.7 s, user 1.7 s, which is the normal path; plugin.cpp:7293). `m_pNewState->Import` runs while `m_pState` is the OUTGOING state. `LoadPerFrameEvallibVars(m_pState)` (state.cpp:1684) writes through `*pState->var_pf_*` (milkdropfs.cpp:469-553), and those are the outgoing state's own VM slots, so the incoming VM receives nothing.
   - **What the blended incoming init sees.** It runs over freshly registered variables, all 0: RegisterBuiltInVariables calls NSEEL_VM_resetvars and regvar (state.cpp:266, 353; ns-eel.h:83 "clears all vars to 0.0"). That means zoom, decay, time, bass, mesh and q are all 0. The same holds for wave and shape init (state.cpp:1750, 1821 write into the outgoing m_wave/m_shape VMs): r g b a samples, x y rad sides num_inst thick ... and q1..q32 are all 0. Rust gives instead the preset values and this state's q_init.
   - **Effect on real presets.** Any init code that reads a registered name before assigning it gets a different captured q, monitor or t, for example `q1=decay;`, wave `t1=q1;`, shape `t1=sides;`, or `t0=time;` when real InitInputs are passed. That changes per-frame output for the whole preset. This is a correctness defect, and no ledger ruling covers it. The doc comment on `from_preset_with` also mischaracterises the C++ as loading "the current preset's values" into this init.
   - **Fix.** The API does not need the outgoing state's values. It needs the load mode, for example `enum InitMode { Instant(InitInputs), Blended }` (or `Option<&InitInputs>`, where None means blended):
     - Blended: load nothing before the preset init, and pass q = 0 and no wave/shape values into wave/shape init.
     - Instant: keep the current behaviour.
     - Split `init_sees_the_preset_values_and_inputs` into both modes, and add a blended test where `q1=decay` gives 0 and wave `t1=q1` gives 0.
     - Alternatively, the controller can rule this a deliberate departure in the ledger and name the cost.
   - ⚠️ I could not measure how many presets are affected: the repository corpus has 35 .milk files and none read an input in init.
